# 09 - Runtime Diagnostics, Profiling & Memory Dump Analysis

Diagnosing high CPU usage, memory leaks, thread starvation, and GC latency in production requires mastery of the .NET Diagnostic CLI tools, EventPipe, and SOS WinDbg extension.

---

## 1. The .NET Diagnostic CLI Tool Suite

Install global diagnostic tools using the .NET CLI:
```powershell
dotnet tool install -g dotnet-dump
dotnet tool install -g dotnet-trace
dotnet tool install -g dotnet-gcdump
dotnet tool install -g dotnet-counters
dotnet tool install -g dotnet-stack
```

| Tool | Purpose | Output Format |
| :--- | :--- | :--- |
| **`dotnet-counters`** | Real-time monitoring of GC heap sizes, CPU %, ThreadPool queue length, and request rates. | Live CLI Dashboard |
| **`dotnet-trace`** | Sampling CPU profiler capturing call stacks, wall-clock time, and flame graphs. | `.nettrace` / Speedscope |
| **`dotnet-gcdump`** | Lightweight GC heap snapshot showing object type counts without freezing the process. | `.gcdump` |
| **`dotnet-dump`** | Full memory crash dump capture and SOS interactive debugger CLI. | `.dmp` |

---

## 2. Real-Time Performance Monitoring with `dotnet-counters`

Monitor live performance metrics of a running .NET process:
```powershell
# List running .NET process IDs
dotnet-counters ps

# Monitor CoreCLR runtime metrics
dotnet-counters monitor --process-id 14520 System.Runtime Microsoft.AspNetCore.Hosting
```

### Key Metrics to Watch:
- `cpu-usage`: CPU utilization %.
- `gc-heap-size`: Total managed memory on GC heaps.
- `gen-0-gc-count` / `gen-2-gc-count`: Rapid increases in Gen 2 indicate high memory churn or large object allocations.
- `threadpool-queue-length`: If queue length stays $> 0$, the thread pool is experiencing thread starvation or blocking calls (`.Result`, `.Wait()`).

## 3. Investigating Memory Leaks with `dotnet-dump` & SOS

### Step 1: Capture Full Process Dump
```powershell
dotnet-dump collect --process-id 14520 --type Full --output memory_leak.dmp
```

### Step 2: Analyze Dump Interactively
```powershell
dotnet-dump analyze memory_leak.dmp
```

### Step 3: Run SOS Inspection Commands

```text
# 1. View heap statistics grouped by type (sorted by total memory size)
> dumpheap -stat

# Output:
# MT                 Count     TotalSize Class Name
# 00007ff8a1234560   54,200    8,672,000 System.Byte[]
# 00007ff8a1239910   120,400  19,264,000 CleanArch.Domain.Entities.ProductItem

# 2. Inspect all instances of a specific MethodTable
> dumpheap -mt 00007ff8a1239910

# 3. Find why an object is not being collected by GC (Find GC Root!)
> gcroot 0000021a89012340

# Output shows the root reference holding it alive:
# -> Static Event Handler in CacheManager
#    -> Subscribed event delegate
#       -> ProductItem instance (Memory Leak Identified!)
```

## 4. JIT Disassembly Inspection (`DOTNET_JitDisasm`)

To inspect the raw x64/ARM64 machine instructions generated by RyuJIT for a specific C# method:

```powershell
# In PowerShell:
$env:DOTNET_JitDisasm = "*SumVectorized*"
dotnet run --project src/CleanArch.WebApi
```

This dumps the exact assembly instructions, SIMD register allocations (`ymm0`), and inlining decisions directly to the console.
